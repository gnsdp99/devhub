# 인프라 설정 최신화 리뷰

## 왜 이 리뷰가 따로 필요한가

인프라 설정은 두 가지 이유로 조용히 썩는다.

첫째, 모델의 지식에는 기준일이 있다. 그 이후에 나온 메이저 버전은 존재 자체를 모르고, "최신"이라고 적어놓은 버전 핀이 실제로는 존재하지 않는 태그일 수 있다. 실제 사례로 Docker Compose 플러그인을 `v2.40.4`로 고정한 설정이 있었는데 조회해보니 이미 `v5.3.1`까지 나와 있었고 `v2.40.4`는 404였다. 부트스트랩 스크립트가 EC2에서 그대로 실패했을 상황이다.

둘째, 인프라 설정의 오류는 문법 검사를 통과한다. `yaml.safe_load`도 `bash -n`도 "이 명령이 이 환경에서 실행될 수 있는가"는 검사하지 않는다. `pip3 install certbot`은 완벽한 문법이지만 Amazon Linux 2023에서는 PEP 668 때문에 반드시 실패한다. 배포하는 순간에야 드러난다.

그래서 이 리뷰는 "코드를 읽고 판단"하는 대신 **바깥의 사실을 조회하고, 의심스러우면 실행해본다.**

## 절차

### 1단계 — 대상 수집

검토 범위의 파일을 모으고, 그 안의 **모든 버전 핀**과 **모든 "어떻게" 결정**을 목록으로 뽑는다.

버전 핀은 명시적인 것만이 아니다. 베이스 이미지 태그, 액션의 `@v4`, 다운로드 URL에 박힌 릴리스 태그, 패키지 이름에 붙은 버전, IaC 프로바이더 제약이 모두 해당한다.

"어떻게" 결정은 대안이 있었는데 하나를 고른 지점이다. 인증서를 어떻게 발급하는지, 사용자를 어떻게 만드는지, 캐시를 어디에 두는지, 태그를 어떻게 붙이는지.

### 2단계 — 근거 확보

**기억으로 버전을 단정하지 않는다.** 조회 방법은 `references/lookup-sources.md`에 명령어째로 정리돼 있다. 핵심만 옮기면 이렇다.

```bash
# GitHub Actions / 릴리스로 배포되는 도구
curl -s https://api.github.com/repos/<owner>/<repo>/releases/latest | grep -m1 '"tag_name"'

# 핀한 버전이 실제로 존재하는지 (낡은 것보다 없는 것이 더 급하다)
curl -s -o /dev/null -w '%{http_code}\n' https://github.com/<owner>/<repo>/releases/tag/<태그>

# 컨테이너 이미지 태그
curl -s "https://hub.docker.com/v2/repositories/library/<이미지>/tags?page_size=100&name=<접두사>"
```

여러 항목을 한 번에 확인할 때는 반복문으로 묶어 한 호출에 끝낸다. 액션이 열 개여도 조회는 몇 초다.

근거의 신뢰도에는 순서가 있다. **공식 문서·릴리스 노트 > 직접 실행해본 결과 > 웹 검색 결과.** 검색 결과는 오래된 내용이 계속 복사돼 도는 경우가 흔하다. 실제로 compose의 `deploy.resources.limits`에 대해 다수의 글이 "`--compatibility` 없이는 무시된다"고 안내하는데, 두 방식을 나란히 띄워 `docker inspect`로 확인하니 둘 다 정상 적용됐다. Compose v3 시절 이야기가 화석처럼 남은 것이다.

그래서 **근거가 엇갈리거나 판단이 갈리면 실측한다.** 컨테이너 하나 띄워 확인할 수 있는 주장이면 띄운다. 반대로 조회만으로 명확한 것(태그 존재 여부, 최신 릴리스 번호)에 실측을 붙일 필요는 없다. 실측은 정확도를 사는 비용이므로 불확실한 곳에 쓴다.

메이저 버전을 올릴 때는 릴리스 노트에서 깨지는 변경을 확인한다. 입력 이름이 바뀌었는지, 기본값이 달라졌는지, 런타임 요구사항이 올라갔는지. 확인 없이 올리면 최신화가 곧 장애가 된다.

### 3단계 — 심각도 분류

발견을 "얼마나 낡았나"가 아니라 **"어떻게 실패하나"** 로 정렬한다. 이 구분이 사용자의 시간을 지킨다.

| 등급 | 뜻 | 예 |
|---|---|---|
| **깨짐** | 실행하면 실패한다. 아직 안 터진 건 아직 안 돌렸기 때문이다 | 없는 태그 핀, PEP 668, dash에 없는 bash 문법, 아키텍처 불일치 |
| **위험** | 동작하지만 보안·운영상 구멍이다 | 가변 태그, IMDSv2 미강제, 암호화 누락, 이미지에 박힌 비밀값 |
| **낡음** | 동작하지만 폐기·레거시 문법이다 | 스펙에서 대체된 키, 구버전 액션, 유지보수 끝난 베이스 이미지 |
| **개선** | 선택적 최적화다 | 레이어 분리, 캐시 전략, 이미지 크기 |

"깨짐"을 먼저 보고한다. 나머지는 미뤄도 되지만 이것은 못 미룬다.

### 4단계 — 보고

아래 형식을 쓴다. 사용자가 훑고 결정할 수 있어야 한다.

```markdown
## 깨짐 — 실행 시 실패

### <항목> — <한 줄 증상>
- **현재**: `<현재 설정>`
- **문제**: <왜 실패하는가>
- **근거**: <조회 결과 / 실측 결과. 명령과 출력을 함께>
- **대체**: `<권장 설정>`

## 위험 / 낡음 / 개선
(같은 형식)

## 바꾸지 않은 것
### <항목>
- **왜 그냥 두는가**: <이유>
```

**바꾸지 않기로 한 것도 반드시 적는다.** 낡았다고 전부 고치는 게 정답이 아닌 경우가 있다. 예를 들어 GitHub Actions 캐시(`type=gha`)는 용량 제한과 간헐적 장애가 알려져 있지만, 대안인 레지스트리 캐시를 쓰려면 PR 워크플로에 클라우드 자격증명을 줘야 한다. 보안 경계를 무르게 하면서 얻을 이득이 아니다. 이런 판단을 적어두지 않으면 다음 리뷰가 같은 항목을 다시 들춘다.

각 항목에 출처 링크를 단다. 사용자가 검증할 수 있어야 한다.

### 5단계 — 적용과 검증

기본은 **보고 후 승인받아 적용**이다. 버전 올림은 깨지는 변경을 동반할 수 있어 사람이 판단할 지점이 필요하다. 다만 사용자가 처음부터 "고쳐줘"라고 했다면 보고와 적용을 함께 진행한다 — 승인을 이미 준 것에 다시 묻지 않는다.

적용 후에는 고친 층위에 맞는 검증을 한다. 문법만 고쳤으면 문법 검사로 충분하지만, 실행 실패를 고쳤다면 실행으로 확인해야 의미가 있다.

```bash
python3 -c "import yaml;yaml.safe_load(open('<파일>'))"   # YAML
bash -n <스크립트>                                          # 셸 문법
docker compose -f <파일> config                             # compose 해석
docker build / docker run                                   # 실제 동작
```

## 문법 검사가 못 잡는 실패

이 축을 별도로 훑는다. 위의 버전 조회로는 절대 안 걸리고, 실제 배포에서만 드러나는 유형이다.

**셸 방언** — Docker의 `CMD-SHELL`, `RUN`, `ENTRYPOINT`의 셸 형식은 모두 `/bin/sh`로 실행된다. Debian·Ubuntu 계열에서 `/bin/sh`는 bash가 아니라 dash다. `/dev/tcp`, `[[ ]]`, 배열, `pipefail`은 dash에 없다. bash 확장을 쓰려면 exec 형식으로 `/bin/bash`를 명시한다.

**패키지 관리자 정책** — 최근 배포판은 시스템 파이썬에 PEP 668 표시를 달아 `pip install`을 거부한다. venv나 pipx가 권장 경로다. 같은 종류로 apt의 외부 관리 표시, `--break-system-packages` 같은 우회의 유혹이 있다.

**아키텍처 가정** — `uname -m`이 뱉는 값(`x86_64`, `aarch64`)과 배포 자산 이름의 규칙이 맞는지, 베이스 이미지에 해당 아키텍처 매니페스트가 있는지. arm64로 옮기면서 이걸 놓치면 이미지가 아예 안 뜬다.

**베이스 이미지 내용물** — slim·jre·distroless 이미지에는 `curl`, `wget`, `bash`가 없을 수 있다. 헬스체크와 진입 스크립트가 이걸 전제하는지 확인한다. 명령 하나를 실제 이미지에서 실행해보면 몇 초에 끝난다.

**권한과 사용자** — passwd 엔트리 없는 숫자 UID로 실행하면 JVM의 `user.home`이 `?`가 되는 식으로, 홈 디렉터리를 쓰는 라이브러리가 나중에 터진다. UID와 GID를 모두 명시해 만들고, `USER`는 숫자로 쓴다.

## 점검 항목

도메인별 구체 항목은 `references/checklist.md`에 있다. Dockerfile, compose, GitHub Actions, 배포 스크립트, AWS 리소스 순으로 정리돼 있으니 검토 대상에 해당하는 절을 읽는다.

## 조회가 실패하면

API가 응답하지 않거나 레이트 리밋에 걸리면, **추측해서 채우지 말고 그 항목을 "확인 불가"로 보고한다.** 기억으로 메운 버전 번호는 이 리뷰가 막으려던 바로 그 오류다. 사용자에게 어떤 항목을 확인하지 못했는지 알리는 편이 훨씬 낫다.
