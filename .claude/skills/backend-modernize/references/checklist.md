## 빌드 스크립트

**버전 관리 방식** — 라이브러리 버전을 개별로 박고 있는지, BOM/플랫폼으로 일괄 관리하는지. 개별 선언은 조합이 검증되지 않은 버전끼리 만나 런타임에 깨질 수 있다. 프레임워크가 BOM을 제공하면 그쪽에 맡기고 예외만 명시한다.

**의존성 스코프** — 컴파일에만 필요한 것이 런타임에 남아 있는지(`compileOnly`), 런타임에만 필요한 드라이버가 컴파일 클래스패스를 오염시키는지(`runtimeOnly`). 스코프가 헐거우면 배포 산출물이 커지고 의도치 않은 API 사용이 컴파일을 통과한다.

**빌드 도구 래퍼** — 래퍼 버전이 지원 중인지. 래퍼 JAR의 무결성 검증이 CI에 걸려 있는지도 본다. 다만 최근 셋업 액션들은 검증을 내장하므로 별도 스텝이 중복일 수 있다 — 실제로 무엇이 이미 하고 있는지 확인하고 중복을 제거한다.

**빌드 성능 옵션** — 설정 캐시, 빌드 캐시, 병렬 실행이 꺼져 있는지. 켜는 것 자체는 쉽지만 빌드 스크립트가 그에 호환되지 않는 방식(설정 단계의 부수효과 등)을 쓰고 있으면 먼저 그걸 고쳐야 한다.

**커스텀 태스크** — 직접 만든 태스크가 프레임워크나 빌드 도구가 이미 제공하는 기능을 재구현하고 있는지.

## 런타임·툴체인

**언어 버전과 지원 상태** — 최신인지보다 **보안 패치를 받고 있는지**가 중요하다. LTS가 아닌 버전을 쓰고 있다면 지원 종료일을 확인한다.

**툴체인 명시** — 빌드가 실행 환경의 기본 런타임에 의존하는지, 툴체인을 명시해 고정하는지. 명시가 없으면 개발자 머신과 CI가 다른 버전으로 빌드해 재현되지 않는 문제가 생긴다.

**새 언어 기능** — 버전을 올려놓고 옛날 문법을 그대로 쓰는 경우가 흔하다. 다만 이건 "개선" 등급이다. 가독성 이득이 분명한 곳만 짚고, 전면 개편을 권하지 않는다.

**동시성 모델** — 런타임이 경량 스레드 같은 새 모델을 제공한다면 기존 스레드 풀 설정이 그와 충돌하지 않는지 확인한다. 두 모델을 섞으면 오히려 성능이 나빠지는 조합이 있다.

## 프레임워크 설정

**설정 키의 유효성** — 프레임워크는 모르는 키를 대개 조용히 무시한다. 이름이 바뀐 키를 그대로 두면 오류 없이 기본값으로 동작한다. **기동 로그의 경고를 읽는 것이 가장 확실한 확인 수단이다.**

**바뀐 기본값** — 메이저 업그레이드에서 가장 위험한 유형이다. 코드도 설정도 그대로인데 동작만 달라진다. 릴리스 노트의 기본값 변경 절을 반드시 확인한다.

**자동 설정 재정의** — 프레임워크가 알아서 해주는 것을 수동으로 다시 만들고 있는지. 과거에 필요했던 우회가 지금은 불필요해진 경우가 많고, 남아 있으면 업그레이드를 막는다.

**프로파일 분리** — 개발·운영 설정이 한 파일에 섞여 있는지, 운영 설정이 개발용 기본값을 상속해 위험한 상태로 뜨는지.

## 웹 계층

**HTTP 클라이언트** — 프레임워크가 새 클라이언트 추상화를 내놓고 기존 것을 유지보수 모드로 돌리는 일이 주기적으로 있다. 무엇을 쓰고 있는지, 대체재가 나왔는지 확인한다. 타임아웃·리다이렉트·응답 크기 제한이 설정돼 있는지도 함께 본다 — 외부 호출에 제한이 없으면 한 곳의 장애가 전체로 번진다.

**오류 응답 형식** — 예외가 그대로 스택트레이스로 나가는지, 표준 형식으로 변환되는지. 클라이언트가 오류를 프로그래밍적으로 처리할 수 있어야 한다.

**입력 검증** — 검증이 컨트롤러에 흩어져 있는지, 선언적으로 처리되는지.

**보안 설정** — 인증·인가 설정 API는 메이저마다 크게 바뀌는 영역이다. 폐기된 설정 방식을 쓰고 있으면 다음 업그레이드에서 확실히 깨진다. 관리 엔드포인트가 필요 이상으로 노출돼 있는지도 확인한다.

## 영속성 계층

**드라이버와 DB 버전 호환** — 연결하는 DB의 메이저 버전과 드라이버·마이그레이션 도구가 호환되는지. DB를 올리면서 도구를 그대로 두면 새 문법을 파싱하지 못한다.

**마이그레이션 도구 설정** — 마이그레이션이 애플리케이션 기동 시 자동 적용되는지, 별도 단계인지. 자동 적용은 편하지만 여러 인스턴스가 동시에 뜰 때의 잠금 동작을 이해하고 있어야 한다.

**커넥션 풀** — 풀 크기가 DB의 최대 연결 수와 인스턴스 개수를 고려해 정해졌는지. 기본값을 그대로 둔 채 인스턴스를 늘리면 DB 쪽에서 연결이 거부된다.

**트랜잭션 경계** — 트랜잭션이 필요한 곳보다 넓게 걸려 있는지. 특히 외부 HTTP 호출이 트랜잭션 안에 들어 있으면 커넥션을 붙잡은 채 대기한다.

**N+1과 지연 로딩** — ORM을 쓴다면 목록 조회에서 연관 엔티티를 개별 쿼리로 가져오고 있는지. 개발 데이터로는 안 보이고 운영에서 터진다.

## 관측성과 운영

**로그 형식** — 운영 환경에서 구조화 로그를 내보내는지. 로그 수집 시스템이 파싱할 수 있어야 검색이 된다.

**민감정보 로깅** — 요청 본문이나 예외 메시지에 자격증명·개인정보가 실리는지.

**헬스 체크의 깊이** — 헬스 엔드포인트가 프로세스 생존만 보는지, 의존하는 DB·외부 서비스까지 확인하는지. 너무 얕으면 죽은 서비스가 정상으로 보이고, 너무 깊으면 외부 장애가 자기 재시작을 유발한다.

**우아한 종료** — 종료 신호를 받고 처리 중인 요청을 마무리하는지. 없으면 배포마다 일부 요청이 끊긴다.

## 테스트

**의존성 대체 방식** — 테스트 컨텍스트에서 빈을 대체하는 API는 프레임워크 메이저마다 바뀌는 대표적인 영역이다. 폐기된 방식을 쓰고 있는지 확인한다.

**컨텍스트 재사용** — 테스트마다 애플리케이션 컨텍스트를 새로 띄우고 있는지. 설정이 조금씩 다른 테스트가 많으면 캐시가 안 먹어 빌드가 몇 배로 느려진다.

**실제 의존성 사용** — DB 테스트를 인메모리 DB로 대체하고 있는지. 문법과 동작이 달라 통과하는 테스트가 운영에서 실패하는 원인이 된다. 컨테이너로 실제 엔진을 띄우는 방식이 권장된다.

**테스트 분류** — 단위·통합 테스트가 구분돼 선택 실행이 가능한지. 구분이 없으면 빠른 피드백이 불가능하다.

## 설정과 비밀값

**비밀값 위치** — 저장소에 커밋된 설정 파일에 비밀값이 있는지. 예시 파일과 실제 파일이 분리돼 있고 실제 파일이 무시 목록에 있는지.

**주입 경로** — 환경변수, 설정 파일, 시크릿 매니저 중 무엇을 쓰는지. 여러 경로가 섞여 있으면 어느 값이 이겼는지 추적하기 어렵다. 우선순위를 명확히 하고 문서에 적는다.

**중계의 중복** — 애플리케이션이 환경변수를 직접 읽고 기본값도 갖고 있는데, 컨테이너 설정이 같은 값을 한 번 더 중계하고 있는지. 한쪽만 고치면 어긋난다.

**타입 안전 바인딩** — 설정을 문자열로 흩어 읽는지, 타입 있는 객체로 묶어 받는지. 후자면 오타와 타입 오류가 기동 시점에 잡힌다.
