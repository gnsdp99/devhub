# 백엔드 최신화 리뷰

## 왜 이 리뷰가 따로 필요한가

백엔드의 낡음은 두 층에서 온다.

**의존성 버전**은 자동화 도구(Dependabot·Renovate)가 어느 정도 잡아준다. 하지만 도구는 "올릴 수 있다"만 알려주고 "올려도 되는가"는 말해주지 않는다. 프레임워크 메이저 업그레이드에는 제거된 API와 바뀐 기본값이 딸려 오고, 그 판단은 릴리스 노트와 마이그레이션 가이드를 읽어야 나온다.

**관행**은 아무도 잡아주지 않는다. 버전을 올려도 코드는 옛날 방식 그대로 남는다. 프레임워크가 대체 API를 내놓고 구식을 폐기 예정으로 표시해도, 경고 하나 없이 계속 동작하기 때문에 몇 년씩 방치된다. 그러다 메이저 업그레이드 때 한꺼번에 터진다.

여기에 모델의 지식 기준일 문제가 겹친다. 기준일 이후에 나온 버전은 존재를 모르고, 기준일 당시 최신이던 관행을 지금도 최신이라고 답한다. 그래서 이 리뷰는 **바깥의 사실을 조회하고, 의심스러우면 컴파일하거나 실행해본다.**

## 절차

### 1단계 — 대상 수집

빌드 스크립트, 프레임워크 설정 파일, 영속성·테스트 구성을 모은다. 그 안에서 두 종류를 뽑는다.

**버전 핀** — 프레임워크 플러그인 버전, BOM, 명시적으로 고정한 라이브러리, 언어·툴체인 버전, 빌드 도구 래퍼 버전.

**관행 결정** — 대안이 있는데 하나를 고른 지점. 어떤 HTTP 클라이언트를 쓰는지, 트랜잭션 경계를 어디에 두는지, 테스트에서 의존성을 어떻게 대체하는지, 설정을 어떤 키로 주입하는지.

### 2단계 — 근거 확보

**기억으로 버전이나 폐기 여부를 단정하지 않는다.** 조회 방법은 `references/lookup-sources.md`에 정리돼 있다. 핵심은 이렇다.

```bash
# Maven Central — 라이브러리 최신 버전
curl -s "https://search.maven.org/solrsearch/select?q=g:<group>+AND+a:<artifact>&core=gav&rows=5&wt=json"

# GitHub 릴리스 — 프레임워크, 빌드 도구
curl -s https://api.github.com/repos/<owner>/<repo>/releases/latest | grep -m1 '"tag_name"'

# 현재 프로젝트가 실제로 해석한 버전 (선언값과 다를 수 있다)
./gradlew dependencies --configuration runtimeClasspath
```

**폐기 여부는 컴파일러에게 묻는 것이 가장 정확하다.** 검색보다 빠르고 틀리지 않는다.

```bash
./gradlew compileJava -Werror --rerun-tasks 2>&1 | grep -i deprecat
```

근거의 신뢰도 순서는 **공식 마이그레이션 가이드·릴리스 노트 > 컴파일러·런타임 경고 > 웹 검색**이다. 검색 결과에는 이전 메이저 시절 내용이 계속 복사돼 도는 경우가 흔하다. 판단이 갈리면 실제로 돌려본다 — 테스트 하나를 실행하거나 애플리케이션을 띄워 로그의 경고를 보는 것으로 대부분 확정된다.

메이저를 올리기 전에는 **마이그레이션 가이드를 먼저 읽는다.** 프레임워크는 보통 버전별 마이그레이션 문서를 따로 낸다. 여러 메이저를 건너뛴다면 중간 단계의 가이드도 봐야 한다 — 제거는 중간 버전에서 예고되고 다음에서 실행되는 식으로 진행된다.

### 3단계 — 심각도 분류

"얼마나 낡았나"가 아니라 **"어떻게 실패하나"** 로 정렬한다.

| 등급 | 뜻 | 예 |
|---|---|---|
| **깨짐** | 지금 실패하거나, 다음 업그레이드에서 확실히 실패한다 | 제거 예정 API, 없어진 설정 키, 지원 종료 런타임 |
| **위험** | 동작하지만 보안·데이터 정합성 문제다 | 취약점 있는 의존성, 노출된 관리 엔드포인트, 트랜잭션 경계 오류 |
| **낡음** | 동작하지만 대체 API가 나왔다 | 폐기 표시된 클래스, 레거시 설정 문법 |
| **개선** | 선택적 개선이다 | 새 언어 기능, 빌드 성능 옵션 |

지원 종료(EOL) 여부를 반드시 확인한다. 보안 패치가 끊긴 버전을 쓰고 있다면 그것만으로 "위험" 이상이다.

### 4단계 — 보고

```markdown
## 깨짐 — 지금 또는 다음 업그레이드에서 실패

### <항목> — <한 줄 증상>
- **현재**: `<현재 코드/설정>`
- **문제**: <왜 실패하는가, 언제 실패하는가>
- **근거**: <조회 결과 / 컴파일 경고 / 마이그레이션 가이드 인용>
- **대체**: `<권장 방식>`
- **영향 범위**: <바꿔야 할 파일 수, 연쇄 변경 여부>

## 위험 / 낡음 / 개선
(같은 형식)

## 바꾸지 않은 것
### <항목>
- **왜 그냥 두는가**: <이유>
```

**영향 범위를 반드시 적는다.** 백엔드 변경은 인프라와 달리 코드 전반에 퍼진다. 한 줄 고치면 되는 것과 계층 전체를 손대야 하는 것은 사용자에게 완전히 다른 결정이다.

**바꾸지 않기로 한 것도 적는다.** 낡았다고 전부 고치는 게 정답이 아니다. 대체 API가 나왔지만 마이그레이션 비용이 이득을 넘거나, 팀이 의도적으로 고른 방식일 수 있다. 이유를 적어두지 않으면 다음 리뷰가 같은 항목을 다시 들춘다.

### 5단계 — 적용과 검증

기본은 **보고 후 승인받아 적용**이다. 프레임워크 업그레이드는 되돌리기 번거로운 연쇄 변경을 만들 수 있어 판단 지점이 필요하다. 사용자가 처음부터 "고쳐줘"라고 했다면 보고와 적용을 함께 진행한다.

검증은 고친 층위에 맞춘다. 백엔드는 인프라와 달리 **테스트라는 검증 수단이 이미 있다.** 이걸 쓰지 않을 이유가 없다.

```bash
./gradlew compileJava          # 컴파일 통과
./gradlew test                 # 회귀 확인
./gradlew build                # 전체
```

테스트가 없는 영역을 고쳤다면 그 사실을 보고에 적는다. "테스트가 통과했다"와 "테스트가 없어서 확인하지 못했다"는 전혀 다른 신뢰도다.

## 컴파일러가 못 잡는 것

버전 조회와 컴파일 경고로 안 걸리는 축이다. 실제로 돌려보거나 설정을 읽어야 드러난다.

**설정 키의 조용한 무시** — 프레임워크는 모르는 설정 키를 대개 조용히 무시한다. 이름이 바뀐 키를 그대로 두면 오류 없이 기본값으로 동작한다. 의도한 값이 실제로 적용됐는지 확인해야 안다.

**기본값 변경** — 메이저 업그레이드에서 가장 위험한 유형이다. 코드는 그대로인데 동작이 달라진다. 릴리스 노트의 "changed defaults" 절을 반드시 읽는다.

**전이 의존성** — 직접 선언하지 않은 라이브러리가 BOM을 통해 따라온다. 취약점은 대개 여기 있다. 선언된 버전이 아니라 실제 해석된 버전을 봐야 한다.

**런타임 전용 실패** — 리플렉션·프록시·자동 설정에 의존하는 부분은 컴파일을 통과하고 기동 시점에 터진다. 애플리케이션을 실제로 띄워보는 것이 유일한 확인 방법인 경우가 있다.

## 조회가 실패하면

레지스트리가 응답하지 않거나 레이트 리밋에 걸리면, **추측으로 채우지 말고 "확인 불가"로 보고한다.** 기억으로 메운 버전 번호는 이 리뷰가 막으려던 오류 그 자체다.
